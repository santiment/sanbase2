# Load Testing

How to generate controlled load against the Sanbase GraphQL API — locally or
against stage — with [k6](https://k6.io/). The test scripts and the local
setup mix tasks live in `load_test/`; see also
[graphql-caching.md](graphql-caching.md) for how the cache under test works.

```bash
brew install k6
```

There are three tests:

| Test | What it measures | Needs local DB |
|------|------------------|----------------|
| `load_test/scripts/graphql_load_test.js` | Realistic mixed traffic (getMetric variants + side queries) | no (with `APIKEY`) |
| `load_test/scripts/cache_saturation_test.js` | Cache behavior under a **controlled hit ratio and response size** | no (with `APIKEY`) |
| `load_test/scripts/cachex_provider_bench.exs` | `CachexProvider` in isolation — no HTTP, no DB, only `:cachex` | no |

## Local setup

Local runs authenticate with API keys generated by mix tasks (require the
local dev DB):

```bash
mix load_test.seed_projects                        # projects + slugs
mix load_test.setup --users 20 --no-rate-limits    # users + apikeys.json
# ... run k6 ...
mix load_test.cleanup                              # deletes *@sanload.test users
```

Generated files (`load_test/data/apikeys.json`, `slugs.json`) are
git-ignored. Without them the scripts fall back to a built-in slug list, and
`APIKEY` (below) replaces the key file.

## Running against stage

The k6 scripts need no local DB or mix tasks — just an API key with no rate
limits. Everything is passed via env:

```bash
cd load_test
export STAGE_APIKEY=...   # keep it out of shell history / the repo

k6 run \
  --env BASE_URL=https://api-stage.santiment.net \
  --env APIKEY=$STAGE_APIKEY \
  --env SCENARIO=rate --env RATE=30 --env DURATION=5m \
  --env HIT_RATIO=0.5 --env WARMUP=1 \
  scripts/cache_saturation_test.js
```

Guidelines:

- Use `SCENARIO=rate` (constant-arrival-rate): request rate stays fixed no
  matter how slow responses get, so the load is predictable and easy to keep
  under the nginx per-IP limits. Start at 20–30 RPS; ramp in later runs.
- Smoke first: `--env SCENARIO=rate --env RATE=5 --env DURATION=30s` and
  check the error rate before a big run.
- Never point the mix tasks at stage — they are local-DB-only; the safety
  guards in `lib/mix/tasks/load_test_*.ex` refuse non-local databases.

## Cache saturation test: controlling hits, misses and entry sizes

`cache_saturation_test.js` shapes the request stream along two axes.

**Hit ratio** (`HIT_RATIO`): every request is either a

- *pool* request — drawn from a fixed pool of `POOL_SIZE` deterministic
  (metric, slug, window, interval) combinations, byte-identical across VUs
  and iterations, so after first touch they are server-side cache **hits**;
- *fresh* request — the time window is shifted by a per-request-unique
  offset larger than the server's TTL key bucket, so the cache key is new: a
  guaranteed **miss** that also inserts a new entry (this is what saturates
  the cache).

`HIT_RATIO=0.9` means 90% pool / 10% fresh. With `WARMUP=1`, `setup()`
primes every pool combination once so pool requests hit from the first
measured iteration.

**Response size** (`DATA_POINTS_PER_QUERY`): a comma-separated mix of
approximate data-point counts per response, default `180,1000,3000`. For
each (metric, target) pair the script uses the metric's `minInterval`
(fetched in `setup()`, snapped up to the nearest step of
5m/15m/30m/1h/2h/4h/8h/1d/7d) and stretches the from/to window so that
`window / interval ≈ target`. Daily-only metrics cap at a 730-day window
(~730 points) — the finest they can do. This inserts cache entries of very
different byte sizes, which is what stresses the memory bound.

Latency is reported per class (`pool_query_duration` vs
`fresh_query_duration`) and requests are tagged `key_class` and
`data_points` for finer breakdowns.

```bash
cd load_test

# The three canonical hit-ratio profiles (local)
k6 run --env HIT_RATIO=0.9 scripts/cache_saturation_test.js
k6 run --env HIT_RATIO=0.5 scripts/cache_saturation_test.js
k6 run --env HIT_RATIO=0.1 scripts/cache_saturation_test.js

# Only big responses (~3000 points each)
k6 run --env HIT_RATIO=0.5 --env DATA_POINTS_PER_QUERY=3000 \
  scripts/cache_saturation_test.js
```

### Environment variables

| Variable | Default | Meaning |
|----------|---------|---------|
| `BASE_URL` | `http://localhost:4000` | Target server; `/graphql` is appended |
| `APIKEY` | — | API key(s), comma-separated; overrides `data/apikeys.json` |
| `SCENARIO` | `load` | `smoke` (2 VUs/30s), `load` (20 VUs/2m), `stress` (ramp to 50 VUs), `rate` (fixed RPS) |
| `RATE` | `30` | req/s for `SCENARIO=rate` |
| `DURATION` | `2m` | duration for `SCENARIO=rate` |
| `HIT_RATIO` | `0.9` | pool (hit) share of requests, in [0, 1] |
| `POOL_SIZE` | `500` | distinct hot combinations backing pool requests |
| `DATA_POINTS_PER_QUERY` | `180,1000,3000` | approximate response sizes to mix |
| `WARMUP` | off | `1` primes the whole pool in `setup()` |

### Fine print

- The pool holds at most `metrics × slugs × data_points_per_query` distinct
  combinations (12 × 20 × 3 = 720 with the built-in lists); a larger
  `POOL_SIZE` logs a warning and effectively caps there.
- The `timeseriesData` cache TTL is 300s + up to 90s per-key offset, so on
  runs much longer than that, expired pool entries are transparently
  re-primed — the observed hit ratio sits slightly below `HIT_RATIO`.
- The cache key does not include the user, so a single API key is enough for
  all VUs to collide on the same pool keys.
- Query complexity is far below the 50k limit even at 3000 points (2 fields
  × 3000 ÷ plan divider), so `DATA_POINTS_PER_QUERY` values into the tens of
  thousands are accepted — response time and payload size become the limit,
  not complexity.

## Observing the server-side cache

From the server's IEx shell while a test runs:

```elixir
SanbaseWeb.Graphql.Cache.count()  # entries
SanbaseWeb.Graphql.Cache.size()   # ETS megabytes
:erlang.memory(:total)            # whole-BEAM footprint
```

`CacheMonitor` also logs stats periodically; see
[graphql-caching.md](graphql-caching.md).

## Cachex provider micro-benchmark

Standalone benchmark of `SanbaseWeb.Graphql.CachexProvider` asserting the
invariants whose violation caused the Cachex 4 OOM incident (bounded ETS
growth, single-flight stampede protection, oversized-value rejection, TTL
sweeping):

```bash
mix run --no-start load_test/scripts/cachex_provider_bench.exs

BENCH_DURATION_MS=10000 BENCH_WORKERS=64 BENCH_MAX_ENTRIES=100000 \
  mix run --no-start load_test/scripts/cachex_provider_bench.exs
```
